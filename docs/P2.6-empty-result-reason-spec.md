## 1. Problem Statement

When an MCP tool call returns `200 OK` with `products: []` and `total: 0`, an agent **cannot tell** whether:

- (a) **no_data** — the catalog genuinely has no product matching this query
- (b) **no_match** — products exist in the category but none match the query terms
- (c) **api_error** — the API is degraded (regression, fabricated-cache, region-down) and is returning empty as a fallback
- (d) **quota** — rate limit or orchestrator quota exhausted at the BuyWhere tier
- (e) **region_unsupported** — the country_code has no merchant coverage
- (f) **category_unsupported** — the category slug is unknown or under taxonomy transition

This is a **product-level distinction**, not just an observability gap. Agents making thousands of decisions per hour cannot act correctly on an empty result without knowing why it's empty. The current behavior conflates "catalog gap" with "API broken" — both look like `200 OK, products: []`.

### Live evidence (Reed, 2026-08-18T23:02Z)

The hourly throughput failure cluster (BUY-71431 SEV-1 → BUY-71454 → BUY-71496 → BUY-71524 → BUY-71536) repeatedly shows `find_best_price` returning `total=0` across all 5 regions, which is **inconclusive to the agent** without a structured reason code. The P1.3 zero-result-rate spec (line 26) explicitly excludes `no error` from the numerator — but the product surface currently does NOT distinguish "no error and genuinely empty" from "no error because the engine gave up".

The monitoring-tier quota exhaustion (BUY-71510) is a separate failure mode that surfaces as `429 RATE_LIMIT_EXCEEDED` from the MCP envelope — but the **agent-side retry logic** has no way to know whether to back off for 60 seconds (quota) or to fall back to a different tool (region_unsupported).

## 2. Acceptance Gate

### 2.1 Wire contract

Every MCP tool response carries a top-level `meta.emptiness_reason` field when `products`/`results` is empty AND the HTTP status is `200 OK`. The reason is an enum:

```json
{
  "products": [],
  "total": 0,
  "meta": {
    "emptiness_reason": "no_data" | "no_match" | "api_error" | "quota" | "region_unsupported" | "category_unsupported",
    "confidence": "high" | "low",
    "diagnostic": {
      "engine_status": "ok" | "degraded" | "fallback",
      "indexed_for_region": true | false,
      "category_recognized": true | false,
      "rate_limit_remaining": 0
    }
  }
}
```

### 2.3 Why this is a P2 item (not P1)

P1.3-NM (BUY-71131) measures **relevance** — products returned but wrong. P2.6 measures **distinguishability** — products not returned, why. They are complementary, not overlapping.

## 3. Design Decisions

### 3.1 Why an enum, not free-form text

Agents parse enums. Free-form text is unparseable and breaks agent reasoning chains. The enum is a closed set to prevent drift.

### 3.2 Why `meta`, not top-level

The current `meta` field already exists for `request_id`, `latency_ms`, etc. Adding `emptiness_reason` keeps the wire contract additive (no v2 bump) and matches the existing pattern.

### 3.3 Why `confidence` on the reason

The engine may not always know definitively — e.g. an empty result from a degraded catalog replica is ambiguous between `no_data` and `api_error`. The `confidence` field tells the agent whether to trust the reason or apply fallback logic.

### 3.4 Why no new HTTP status

A 200 OK with a structured `emptiness_reason` is more useful for agents than a 503 because:
- Agents already retry on 5xx; if the underlying cause is `no_data`, the retry is wasted.
- A 200 with `confidence: low` lets the agent decide whether to retry vs degrade gracefully.

### 3.5 `confidence` field semantics (Reed decision, 2026-08-19T2210Z)

`confidence` is a signal to the agent about whether to **trust the reason or apply its own fallback logic**. It is NOT about the truth-value of the data returned — when an empty is returned, the data is empty. `confidence` describes the certainty of the engine's *classification* of the cause.

| `confidence` | Meaning | Agent behavior |
|---|---|---|
| `high` | Engine is confident this is the cause. Detection heuristics §4 fired cleanly with no ambiguity. | Treat the reason as authoritative. Do not retry; route to the documented next-step for that reason. |
| `low` | Engine could not definitively classify — likely between two reasons (e.g. `no_data` vs `api_error` when a degraded replica returns 0). | Apply agent-side fallback: retry once after a short backoff (≤2s); if still empty, surface as ambiguous to the user. |

**When to emit `low`** (concrete rules):
- Engine replica returns 0 but a degraded/fallback replica also returns 0 in the last 5 minutes → `low` (ambiguous between `no_data` and `api_error`)
- `region_unsupported` paired with no `country_code` default → `low` (agent may have omitted the field)
- `category_unsupported` paired with `category_recognized: false` but query terms match a known category slug → `low` (taxonomy drift)
- All other cases (clean replica agreement, recent SEV-1 fired, rate-limit guardrail hit cleanly, etc.) → `high`

**Why this matters for the 225-cell sweep (Cart, BUY-71543):** the sweep MUST record `confidence` per cell and flag a regression when `confidence: low` rate exceeds 5% over a 24h window — that is the proxy for "the engine is unsure", not a data-correctness gate.

## 4. Detection Heuristics (Rex implementation guide)

| Reason | Detection |
|---|---|
| `no_data` | Engine returns 0 rows, all replicas agree, no recent SEV-1 alert |
| `no_match` | Engine returns 0 rows but category + region have indexed products; query terms fail relevance gate |
| `api_error` | Engine replica returns 5xx OR recent SEV-1 alert exists OR pipeline marker present |
| `quota` | Rate-limit guardrail triggers inside the orchestrator before the engine |
| `region_unsupported` | Country code not in `supported_regions` table |
| `category_unsupported` | Category slug not in `category_taxonomy` after the BUY-70699 taxonomy fix ships |
