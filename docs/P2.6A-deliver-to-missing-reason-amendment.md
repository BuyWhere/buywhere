# P2.6A — `deliver_to_missing` reason (v1 surface amendment)

**Owner:** Reed (CPO) — spec, sign-off
**Eng owner:** Rex (CTO) — wire (small additive change, scope to the empty-result path)
**Review owner:** Cart (Agent Success Lead) — adopt-rate on 225-cell sweep
**Parent spec:** [P2.6-empty-result-reason-spec.md](./P2.6-empty-result-reason-spec.md) §3.5 (`confidence` semantics) and §4 (detection heuristics)
**Parent roadmap:** BUY-70699
**Horizon:** ships **with P2.7 v2 wire** (BUY-71817) — same PR or one PR after

## TL;DR

The P2.6 enum is missing the single most common empty-result cause today: **the agent omitted `deliver_to`, so the engine returned globally-ranked results that did not pass the per-country deliverability gate, so the response is empty even though products exist for at least one region**. We add one enum value, `deliver_to_missing`, that lets the agent self-correct without guessing.

This is the **bridge spec** between P2.6 (empty-side distinguishability) and P2.7 (non-empty-side REQUIRED `deliver_to`): it gives v1 callers an actionable signal today, while the v2 surface finishes deploying.

## Problem statement

Today, an agent that calls `search_products(q="laptop")` without `deliver_to` receives either:

- a non-empty result set where most rows are not deliverable to its user (the **non-empty** case — P2.7), or
- an empty result set when the relevance/availability filter strips globally-ranked rows (the **empty** case — P2.6 today, but with no reason code).

The agent cannot tell from `200 OK, products: []` whether:

1. the catalog truly has no laptop products (P2.6 `no_data`),
2. the catalog has laptops but the query is wrong (P2.6 `no_match`),
3. the catalog has laptops but **none were shippable to the unspecified `deliver_to`** (new — P2.6 gap), or
4. the API is degraded (P2.6 `api_error`).

Cases (3) and (1) collapse to "empty" today. Cart's adoption telemetry (94% of calls omit `deliver_to`) means case (3) is the **dominant empty** today. Without a reason, agents either retry pointlessly or conclude the API is broken.

## Wire contract — additive on P2.6

Add **one enum value** to the P2.6 `meta.emptiness_reason` set:

```
meta.emptiness_reason ∈ {
  no_data,
  no_match,
  api_error,
  quota,
  region_unsupported,
  category_unsupported,
  deliver_to_missing   ← NEW
}
```

### When to emit `deliver_to_missing`

Emit `deliver_to_missing` (with `confidence: high` unless the rule below says otherwise) when **all** of:

1. The request did NOT include `deliver_to` AND did NOT include `country_code` (alias `country` accepted too) — i.e. the agent truly gave the engine no location to filter on, AND
2. The engine's relevance + availability filter produced 0 rows after global-rank → per-region availability pruning, AND
3. The query term matches a category + region with ≥1 indexed product (i.e. the cause of the empty is the missing `deliver_to`, not a catalog gap).

If condition (1) is true but (3) is false (no indexed products for any region the engine can serve), emit `no_data` instead — do not blame the agent for an empty that is genuinely a catalog gap.

### `confidence: low` override

Set `confidence: low` (instead of `high`) when:

- The request omitted `deliver_to` AND `country_code`, AND
- The query term is ambiguous (matches >1 category in the taxonomy) AND
- Catalog has ≤5 indexed products for any of those categories.

The agent's fallback here is: re-issue the call with `deliver_to=<ISO>` (most likely fix). The low-confidence hint signals "we believe the cause is the missing `deliver_to`, but the catalog is thin enough that we cannot rule out `no_data`".

### Diagnostic block extension

Add one diagnostic field to the P2.6 `meta.diagnostic` block (additive):

```json
"diagnostic": {
  "engine_status": "ok" | "degraded" | "fallback",
  "indexed_for_region": true | false,
  "category_recognized": true | false,
  "rate_limit_remaining": 0,
  "deliver_to_present": true | false   ← NEW
}
```

This lets the agent verify (without re-parsing the request) that the engine actually saw the absence of `deliver_to`. Set `false` iff the request omitted both `deliver_to` and `country_code`/`country`.

## Out of scope

- The v2 tool surface where `deliver_to` is REQUIRED (P2.7 / BUY-71817). P2.6A does NOT change v2 behavior; v2 callers must include `deliver_to` and will never trigger `deliver_to_missing`.
- A new HTTP status. P2.6A inherits the additive `meta` pattern.
- Removing `verify_deliverable` (single-product tool). v2 makes it redundant; P2.6A does not change it.

## Rollout

1. **Same PR as P2.6** (preferred) — Rex ships `deliver_to_missing` + `deliver_to_present` diagnostic as part of the P2.6 enum extension. One PR, additive.
2. **Or one PR after P2.6** — if Rex scopes P2.6 narrowly, ship P2.6A as a follow-up.
3. Cart updates the 225-cell sweep to record `deliver_to_missing` per cell and flag a regression if the rate changes ±5% week-over-week.

## Why this is P2.6A (not a new P2.7 amendment)

- P2.7 changes the **input contract** (REQUIRED `deliver_to` on v2). Ships with v2 wire.
- P2.6A changes the **output contract** for v1 callers when they omit `deliver_to`. Ships on the v1 surface, alongside P2.6.
- The two together give a complete loop: agents on v1 self-correct via the reason; agents on v2 cannot make the mistake.
