# BUY-73800 — Fix evidence (2026-08-25 11:21Z by Probe 2)

## What was wrong
`canonical_throughput_hourly.reconciliation_status` was stuck at `UNKNOWN`
for every recent hour because `getCounterProductsReconciliation` and
`get24hAlignmentWindow` both ran `COUNT(*) FROM products WHERE created_at ...`
on a 406GB table without a `created_at` index. Every run hit the 30s
statement_timeout.

Evidence before fix (live sakura catalog, 2026-08-25 10:30Z):
```
 hour_start                 | ing_inserted | reconciliation_status | reason
----------------------------+--------------+-----------------------+-----------------------------------------------
 2026-08-25 10:00:00+00     |           16 | UNKNOWN               | products.created_at COUNT timed out; cannot reconcile
 2026-08-25 09:00:00+00     |          202 | UNKNOWN               | products.created_at COUNT timed out; cannot reconcile
 2026-08-25 08:00:00+00     |          626 | UNKNOWN               | products.created_at COUNT timed out; cannot reconcile
 2026-08-25 06:00:00+00     |            0 | UNKNOWN               | products.created_at COUNT timed out; cannot reconcile
 ... (every recent row UNKNOWN)
```

## Fix
Commit `cc0f051d` on `main` (BuyWhere/buywhere):
`fix(BUY-73800): emit DRIFT/DRIFT=0 without products.created_at COUNT`

Three-path fallback for the products leg:

1. **`short_circuit_ing_inserted_zero`**: when `ing_inserted=0` for the hour,
   emit `ALIGNED` with `DRIFT=0 (short-circuit)` reason. No COUNT runs.
2. **`canonical_delta_ins_from_stats`**: when the dispatcher populated
   `delta_ins_from_stats` (pg_stat delta), use that bounded integer. No COUNT.
3. **`direct_products_count`**: legacy fallback, still wrapped in try/catch.

Same logic applied to `get24hAlignmentWindow` — replaced the products COUNT CTE
with a read of `canonical_throughput_hourly.delta_ins_from_stats`.

Removed the `SELECT MAX(created_at) FROM products` diagnostic — second source
of timeouts, no operational value.
